# Troubleshooting

Start with `spyria doctor`: it checks Docker, each service and its healthcheck, the server's start check (the list of settings it refuses), the disk and the image versions, and what exposes the install: a `.env` other users of the machine can read, a missing, default or short credential in it, and a port a service publishes beyond the machine. `spyria compose logs <service>` shows a service's logs, for example `server`, `zero-cache`, `gateway` or `host`.

| Symptom | Cause and fix |
|---|---|
| `spyria setup` says this machine holds the data of an earlier deployment | The install folder has no `.env` with the secrets of that deployment, while its Postgres, zero-cache and gateway volumes are still on the machine: new secrets would not open them. Put back the `.env` you copied off the machine with your [backups](./operations.md#backups) and run setup again, or choose another deployment name with `--name`. To start over without that data, remove the volumes setup names with `docker volume rm`. |
| `spyria doctor` says `.env` is readable by other users | Something rewrote it with a wider mode: `chmod 600 .env` in the install folder. Setup and `spyria upgrade` write it readable by you only. |
| `spyria doctor` names a default or short credential | Most take a new value from `openssl rand -hex 32` in `.env`, then `spyria compose up -d`. Three cannot simply change: `SPYRIA_SECRETS_KEY` is [rotated](./operations.md#rotating-the-secrets-key), or the stored SSO secrets and GitHub App keys are lost; `SPYRIA_GATEWAY_ENCRYPTION_KEY` changes only with the gateway's database wiped, after which members add their API keys again; for `SPYRIA_POSTGRES_PASSWORD` (role `spyria`) or `SPYRIA_GATEWAY_DB_PASSWORD` (role `bifrost`), Postgres keeps the password it started with, so set the new one there first: `spyria compose exec postgres psql -U spyria`, then `\password spyria` or `\password bifrost`. |
| `spyria doctor` says a service publishes a port | A `compose.yml` edited by hand publishes it on every address: publish it on `127.0.0.1` only, or remove it; Cloudflare's tunnel reaches the server without any published port. |
| The server keeps restarting | The production check failed: `spyria compose logs server` lists every problem, and `spyria doctor` shows them too. |
| `502` from the proxy | The proxy forwards to `https://`. The server speaks plain HTTP on the Compose network: use `http://server:3000`. |
| The app loads but never syncs | The proxy drops WebSocket upgrades on `/zero/`, or zero-cache is down: `/health` answers `503` naming `zero`, and the server logs `zero.unreachable`. |
| A prompt says the runtime image is missing | The host could not pull it: `docker logs <deployment>-host` has the registry's reason. A host built from a clone (no `SPYRIA_IMAGES`) accepts only a local content ID: run `bun run agent:build` there, or load the same image. |
| The host profile cannot reach Docker | `SPYRIA_DOCKER_GROUP` is not the group of `/var/run/docker.sock` (Linux), or Docker runs rootless. |
| SSO client secrets or GitHub App keys stop working | `SPYRIA_SECRETS_KEY` changed without the previous value in `SPYRIA_PREVIOUS_SECRETS_KEYS`. Put it back there; otherwise enter every secret again. To change the key, [rotate it](./operations.md#rotating-the-secrets-key). |
| Members' API keys stop working | `SPYRIA_GATEWAY_ENCRYPTION_KEY` changed. Restore it; otherwise wipe the gateway's database and have members add their keys again. |
| Runtimes stop starting after many chats | The host ran out of Docker address pools; see [Many runtimes on one host](./self-hosting.md#many-runtimes-on-one-host). |
| `spyria setup` stops at the Cloudflare step | The API token lacks a permission: *Account > Cloudflare Tunnel > Edit*, *Zone > DNS > Edit* and *Zone > Zone > Read*, plus the Access and Email Routing ones for those steps (`spyria --help` lists them). |
| Docker refuses `spyria setup` on Linux | Your user is not in the `docker` group: `sudo usermod -aG docker $(id -un)`, log out and back in. |
| The first workspace's link says the deployment is being set up | The link lacks the setup token, or a workspace already exists: `spyria setup-link` prints it again while none exists. |
| Sign-in says "Your provider did not confirm this address" | The provider sent no `email_verified: true` for the address. Through a generic OIDC provider, add a claim mapping that sends it ([who can join](./who-can-join.md)); through Google, the account is not a confirmed one. |
| Microsoft sign-in refuses personal accounts or accounts of other organizations | The deployment's Microsoft app is registered for one directory only: in Microsoft Entra, set its supported account types to *Accounts in any organizational directory and personal Microsoft accounts*. |
| Sign-in says the address "already signs in with another account" | Another account was bound to that address first, at this provider or another. Sign in with that account. |
| A runtime host shows **Update needed** and stays offline | Its protocol is older than the server's minimum: run the command its badge shows on that machine. |
| On a cloud, the site answers `503` for a while after a restart | zero-cache rebuilds its replica from Postgres at each start; the server itself stays up (`/health/live`). |
| On Azure, the hostname has no HTTPS | Run the `certificate_command` output once the DNS records exist ([cloud](./cloud.md)). |
| On Google Cloud, the certificate stays provisioning | The hostname's `A` record must point at the load balancer's address before Google issues it; this takes up to an hour. |
