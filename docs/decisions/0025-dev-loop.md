# 0025. The dev loop: server-run steps between the agent's turns

## Context

A dev chat today stops at the agent's own judgement: it writes code, maybe runs the checks it thinks of, and the owner finds out on the pull request whether lint, types, tests or CI pass. Every round trip after that ("fix the failing test", "address the review comments", "resolve the conflicts") is a prompt the owner types or a button they press. Large teams that run coding agents at scale converged on the same shape: deterministic steps the orchestrator runs itself, interleaved with agent turns, with a hard cap on rounds and a human at the end ([Stripe's minions](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents) allow at most two CI rounds; [Anthropic's code review](https://claude.dev/blog/solving-code-review-at-anthropic) caps author–reviewer rounds at three after one pull request went through more than 50 rounds overnight, mostly on code that predated it).

Nothing in Spyria started a turn without a member's prompt, and publishing was reserved to the owner's own prompts ([0011](0011-publishing-through-server-side-bundles.md)). The setup script ran alongside the first turn with no time limit and never again after a restart.

## Decision

- **The loop is the chat's own turns, not a new entity.** After an agent turn, the server runs the steps the repository defines and, when one fails, prompts the agent again. Each automatic prompt is a message of the owner marked as sent by the loop; the loop's state (phase, rounds, check results, review findings, pull request) is a **Dev loop** card in the chat, updated in place like the pull request card. The loop runs in every dev chat, on Spyria's runtimes and on members' machines alike, since both run the same `spyria-agent`.
- **Automatic turns count as the chat owner's prompts.** They use the owner's key and budget and may publish, like the owner's own prompts; the event records a system actor `dev_loop` acting on behalf of the owner ([0024](0024-typed-actors-on-events.md)). Only the owner's own prompts start a loop: a guest's prompt runs as one turn with the guest's rights, as before ([0009](0009-agent-acts-as-the-owner.md)), so nobody gains the owner's key, budget or push through someone else's chat. A ticket-started loop (v2, its own decision) uses the ticket's assignee as the owner.
- **The agent ends the work explicitly** by calling `finish_work` with the pull request's title and description; it is a tool on the `github` tool server, which every harness gets, listed only when the loop is on. After that turn the server verifies the claim: the checks, then the review, then the push and the pull request, then CI. A failure sends the agent back with the failure as untrusted tool output, and the agent calls `finish_work` again when it is done. A turn that ends without `finish_work` means the agent is waiting for the owner: the loop stops, with no automatic turn and no push.
- **Where settings live.** The repository's `.spyria/dev-loop.json` names the check commands and the CI checks that count; `REVIEW.md` and `AGENTS.md` guide the reviewer. The **Dev loop** card in Workspace settings, for members who can connect GitHub, turns the loop on and sets its limits. Members bring their own models, so the workspace never picks a model for a step.
- **Checks run in the runtime, in the background.** `spyria-agent` runs them one after the other with the setup script's environment and a time limit each; the server polls their state, since the host relay holds no request longer than 2 minutes.
- **The review is a fresh context, judged by the server.** The loop asks the agent to start a subagent with a fresh context (its harness's own: Pi's `delegate`, Claude Code's subagents) on the branch's diff, or on what changed since the last review, then to call `report_review` with each finding tagged important, nit or pre-existing. Only important findings that were not reported before send the agent back; nits and defects in code the diff did not change never block.
- **The loop converges.** Each phase has a number of fixes (checks 3, review 3, CI 2 by default; 0 turns the review off or skips CI), the loop has a time limit, and chats on an API key have a cost limit per loop, counted from the model calls of the chat since the owner's prompt; on a member's machine, subscriptions are not metered, so only the fixes and the time limit apply. Past its fixes, a phase asks the agent to say what it would change about the approach instead of fixing again, then hands over. Any limit, or all green, hands over to the owner with a notice: "ready for your review", never "approved".
- **Members come first.** Any member's message stops the loop and the automatic prompt it queued, including a message written before the loop started; so do **Stop** and turning the loop off, which the audit log records. The owner's monthly budget is checked before each automatic step, not only at the relay ([0014](0014-hard-stop-budgets.md)).
- **CI is read the way `read_checks` reads it** ([0021](0021-ci-on-github-actions-through-develop.md)): the server polls the check runs of the pushed head every minute, judges them once every counted check has finished, and gives the agent the failing ones with their annotations and, for a GitHub Actions job, the failed step and the end of its log. Pull request cards key their checks by run id, not by name, so the loop does not judge from them. When no counted check reports within 15 minutes, the loop hands over.
- **Setup comes first.** Prompts wait for the setup script; it has 45 minutes, after which its process group is stopped; it runs again each time the runtime starts.

## Consequences

- Publishing is no longer only on the owner's typed prompt: the loop pushes, but only after `finish_work`, green checks and a review without important findings. The owner agreed to it by working in a dev chat of a workspace whose admin turned the loop on.
- An App that has not accepted `actions: read` gives the loop annotations only, as it does `read_checks`.
- CI logs and test output reach the owner's model provider. GitHub masks the secrets it knows about; anything else a job prints goes along.
- Setup scripts must be safe to run twice.
- Ticket intake comes after, with its own decision.
